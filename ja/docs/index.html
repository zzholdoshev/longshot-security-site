Longshot 2.18.1 — 一般的なチュートリアルとコントロールのリファレンス

ロングショットについて 2026 年 11 月 10 日更新 2.18.1 (Firefox および Chrome エディション) とその ネイティブ HTTP/HTTPS ツール プロキシ。これは、一般的な 2.11.1 チュートリアルを置き換えます。以下の手順では、出荷された実装について、その制限も含めて説明します。古いブリッジの例は、このリリースと互換性がありません。

Longshot は、承認された Web アプリケーションを評価するためのブラウザー セッション ワークベンチです。これは、検出、独自の JavaScript アクティブ スキャナー、手動 HTTP ツール、インポートされたテンプレート、検出結果のレビューとレポートを組み合わせたものです。オプションのブラウザ ブリッジを使用すると、外部ツールが独自のネイティブ HTTP リクエストを送信しながら、選択された Firefox セッション値を使用できるようになります。

便利な最初のパスは次のとおりです。 アプリケーションを開く → サインイン → そのタブから Longshot を起動 → 接続 → セッションを検証 → 入力を検出 → 選択したチェックを実行 → 証拠を確認.

AI で構築されたアプリケーションやバイブコーディングされたアプリケーションなど、ユーザーの機密データや金銭を扱うアプリケーションの場合は、サイバーセキュリティ チームを雇って専門的な評価を依頼してください。拡張スキャンは、認可テスト、ビジネス ロジック レビュー、または独立したセキュリティ評価に代わるものではありません。空の所見リストはセキュリティ証明書ではありません。

このドキュメントではコマンドについて説明します。更新しても、ソフトウェアのインストール、ホストの登録、ブラウザ設定の変更、スキャンの実行は行われません。許可された評価ターゲットに対してのみサンプルを実行してください。サンプル http://localhost:8080 これはローカル ターゲットの例であり、組み込みの Longshot サービスではありません。

出版ノート

アカウント損失の話は仮説であり、実際の顧客に関する主張や、ロングショットが経済的損失を防ぐという保証ではありません。この拡張機能は、継続的な攻撃のブロックではなく、評価を実行します。調査結果は再検討が必要です。カバレッジ表では、限定されたサポートと手動のみのギャップについて説明します。 DOM 分析には、普遍的な DOM エクスプロイトをカバーするものではなく、インジケーターとサポートされている実行カナリアが含まれます。映画のようなシーケンスは証拠を説明します。悪用の証拠は追加されません。

MCP とブラウザ ブリッジはローカル設定が必要です。ネイティブ ツール プロキシは別の Node/Python/mitmproxy プロセスを使用し、HTTPS インターセプトにはアダプター CA に対するツールの信頼構成が必要です。これは、バイト透過的な生の TCP ではなく、解析された HTTP トランスポートです。 Cookie の上書きは無効にすることができます。ブラウザの Cookie やユーザー エージェントは、ブラウザと同一のネットワークや WAF の受け入れを保証しません。外部 ZAP は別途インストールされたままになります。テンプレートの実行は互換性/ランタイムに依存します。 OAST には構成されたプロバイダーが必要です。認証検証には、意味のある保護されたエンドポイント/マーカーが必要です。ターゲット プロファイルは評価データを分離します。タブ/コンテナは Cookie セッションを提供します。

機密データや金銭を扱うアプリケーションの場合は、サイバーセキュリティ チームを雇い、評価の一部として Longshot を使用します。自分が所有するアプリケーション、またはテストを許可されているアプリケーションでのみ使用してください。

積極的なオプションと実行承認

アグレッシブでは、明示的に承認されたメソッド/機能が有効になります。すべてのチェックを実行したり、より強力な証拠を保証したりするものではありません。

  1. 最初に入力を検出し、認証を検証します。
  2. 必要な詳細オプションと書き込み/アップロード/削除権限のみを有効にします。
  3. スキャン オプションを保存します。
  4. 選択してください 次の積極的な実行をレビュー/承認する.
  5. ターゲット、機能、メソッドの権限、予算を確認します。
  6. クリック 次回の実行を承認する。このユーザーアクションは、不足している統合された Firefox 権限を要求し、次回実行の許可を作成します。
  7. 確認した構成で実行を開始します。

この付与は 1 回限りの使用で、30 分後に期限切れになり、関連するターゲット/構成/リクエスト設定の変更によって無効になります。通常、新しいスキャンには新しい許可が必要です。未完成のオプションを保存することは許可されています。開始または承認では、必須フィールドが検証されます。

Firefox に必要なもの permissions.request() 実際のユーザーのアクションから直接発生します。設定の変更は、バックグラウンドで任意の権限を付与する理由にはなりません。権限が拒否された場合は、正確な機能を確認し、承認ボタンから再試行するか、その機能を無効にしてください。通常の OS/ブラウザ許可プロンプトは、拡張機能 DOM オートメーションの範囲外のままです。

最大の検出結果は広範囲にプリセットされています

このプリセットは、高度な検証、OAST およびセッション B の比較を含む多くのフェーズを有効にし、いくつかの予算を拡張します。これは「すべてを見つける」スイッチではありません。 OAST アカウントの作成、プロバイダー URL/コールバック ドメインの入力、有効なセッション B の選択、Nuclei のインストール、不足しているロールの認証は行われません。

承認によって空の OAST フィールドまたはセッション B の欠落が報告された場合は、それらを設定するか、それらのオプションをオフにします。これは、ターゲット URL が有効かどうかとは別のものです。

  • カテゴリ: custom, waf, sqli, nosqli, code, xss, ssti, traversal, crlf, redirect, command.

パックはターゲット固有であり、最初は 無効化された。プレビューを確認し、目的のパックを明示的に有効にします。有効化されたアップロードされたパックには、積極的な承認が必要です。アップロードだけでは何も実行されません。

制限: ペイロード ファイルあたり 256 KB、パックあたり 200 文字列、値あたり 2,000 文字、ターゲットあたり最大 10 パック / 500 値 / 512 KB のパック構成。パック内の重複する文字列は削除されます。既存の方法、範囲、予算、および破壊的 SQL ガードは引き続き適用されます。

分類されたパックは、組み込みのクラス値を補完します。 WAF パックにはさらに、スマート バリエーションと適格なフィルタリングの証拠が必要です。リテラル カスタム ペイロードは、予期される出力マッチャーや実行可能な拡張コードではありません。 CVE 番号をアップロードするだけでは、その CVE を検証できません。

YAML/YML/JSON をアップロードする前に、CVE/Nuclei テンプレート カテゴリを選択してください。テンプレート ファイルの上限は 2 MB です。でレビューしてください テンプレート、実行者と具体的な準備完了/ブロックされた理由を含む。インポートされたテンプレートは共有ライブラリを使用します。ペイロード パックはターゲットに留まります。

  • 選択したものを実行 選択したテンプレートを直接実行し、CVE 自動フェーズを必要としません。
  • CVEオートフェーズ 構成されたスキャン中に、適格な CVE タグ付き/識別されたインポートを考慮します。
  • オートファズ 一般的な値を生成します。作成された CVE ペイロードやマッチャーは書き換えられません。

レビュー済みの相対ヘルパー バンドルを、それらを必要とするテンプレートとともにインポートします。使用できないネイティブ ランタイム、範囲外のリクエスト、承認の欠如、またはサポートされていない機能は検査の理由であり、ネガティブ テストの成功ではありません。

サーバースタックとスマートアナライザー

使用する ソフトウェアの検出 サポートされている範囲の観察を収集します。遺体の証拠が必要な場合は、代表的なページを閲覧し、適切な応答を保存してください。次に選択します 記録された証拠を分析する 最大 200 件の最近保存された応答のローカルな受動的相関。アナライザー自体はターゲット リクエストを追加しません。

このビューでは、ブラウザー コンポーネント、WAF/CDN/エッジ、Web サーバー/リバース プロキシ、およびアプリケーション/ランタイム信号が分離されています。製品固有のヘッダー、Cookie 名、アセット/ブートストラップ構造、およびエラー テキストにより、信頼性が高まります。チャレンジ ページの本文は、アプリケーションのフィンガープリンティングから除外されます。一般的な 403、nginx バナー、または CDN エッジは、特定の WAF ルールが有効であることを確立しません。

考えられる構成カードでは、その証拠と推奨される検証について説明します。これらは仮説です。ブラウザーの応答では、発信元 IP、プライベート サブネット、バックエンド データベース設定、TLS 終端、ファイアウォール ルール、またはプロキシ信頼リストを正確に確立することはできません。複数のアップストリームと書き換えられたバナーにより、レイヤーが隠蔽されたり、誤って認識されたりする可能性があります。

WAF の推奨事項とレート処理

保守的なスキャン推奨事項を適用する コミュニティ SQL プローブ、スマート バリエーション、および適応レートを明示的に有効にし、設定されたレートを最大 0.5 リクエスト/秒に下げます。スキャンを開始したり、高度な機能を付与したりすることはありません。

適格な調査は、既存の予算内で最大 3 つの代替案を考慮します。ブロックされたベースラインはスキップされます。ブラウザチャレンジには通常のブラウザ解像度が必要です。通常の ACL 拒否では、無限のバイパス試行が正当化されるわけではありません。ブロックから許可への変更は到達可能性の証拠であり、脆弱性の証拠ではありません。

明示的なチャレンジを繰り返すと、メモリ内レートが半減し、少なくとも 10 秒の待ち時間が発生する可能性があります。 Retry-After を使用した HTTP 429 または 503 は、スケジュールされたさらなるプローブを停止します。より長い Retry-After 間隔が尊重されます。レートが自動的に再び上昇することはありません。新しい実行は設定されたレートで開始されます。

CVEルックアップ

オンライン CVE を検索する 許可後にサポートされる製品/パッケージの座標を NVD/OSV にクエリします。リクエストでは、ターゲット URL、Cookie、ページ コンテンツではなく、座標が送信されます。不明なバージョン、ベンダーのバックポート、未検証のパッケージの存在により、結論は限定されます。手動の npm/PyPI エントリはインストールを証明しません。

一致しないことは、CVE がないことを意味するわけではありません。一致は助言候補です。前提条件を調べて使用する 検証テンプレートを見つける 適切なインポートされた小切手を見つけます。このボタンは、テンプレートを実行するのではなくフィルタリングします。

  3. 一致するものを入力してください コールバックドメイン なしで http://、ポートまたはパス。
  4. 入力してください プロバイダートークン そのプロバイダーが要求した場合のみ。
  5. TTL とポーリング間隔を設定します。 OAST と関連する SSRF/XXE/Log4Shell/コマンド オプションを有効にします。
  6. 使用する OAST接続をテストする 登録/投票を確認します。
  7. 使用する OAST コールバックをテストする このブラウザから別の相関カナリアを送信します。
  8. 実際のスキャンを保存、確認、承認します。 OAST インタラクションにおける正確な相関関係とプロトコルを検査します。

たとえば、次の場所で一致する公共サービスを使用する場合、 https://oast.pro、そのコールバックベースは oast.pro。これは一例であり、可用性の保証やそのプロバイダーの使用要件ではありません。セルフホステッド プロバイダーには、適切に委任された独自の到達可能なドメイン、DNS/リスナー、および TLS が必要です。ラップトップの HTTP リスナーだけではパブリック コールバック サービスではありません。フォローする 公式Interactshセットアップ.

ブラウザ ブリッジ: ネイティブ ツール プロキシ

送信内容

外部ツールは、攻撃ペイロード、メソッド、本文、クエリを含むリクエストを生成します。ネイティブ アダプターは、mitmproxy を介してそれを転送し、構成された Cookie/ヘッダーの変更のみを適用します。それはあります そうではない Firefox に、ZAP または別のツールに代わってフェッチを実行するように依頼します。

これにより、ネイティブ HTTP セマンティクスとツールのペイロード生成が保持されますが、任意の元のワイヤ バイトは保持されません。mitmproxy は HTTP を解析/シリアル化し、独自の送信 TLS 接続を確立します。ブラウザーのユーザー エージェント文字列によって、ネイティブ TLS/ネットワーク フィンガープリントが Firefox と同一になるわけではありません。

HTTPSの信頼

アダプターは、通常、選択されたデータ ディレクトリの下に独自のローカル CA を生成します。

run/ca/mitmproxy-ca-cert.pem       public CA certificate for tool trust
run/ca/mitmproxy-ca.pem            sensitive CA material/private key

を設定します。 外部ツールの評価信頼構成 起動時に公開証明書パスが出力されます。秘密キーを共有したり、システム/Firefox トラスト ストアが変更されたと想定したりしないでください。アダプターは、その CA をどちらの信頼ストアにもインストールしません。

カールの場合:

curl --noproxy '' \
  --proxy http://127.0.0.1:8900 \
  --proxy-user 'bridge:CURRENT_TOKEN' \
  --cacert /absolute/path/to/native-bridge/run/ca/mitmproxy-ca-cert.pem \
  'https://actual-target.example/search?q=apple'

交換する CURRENT_TOKEN およびターゲット/証明書のパス。 HTTP のみのローカル ターゲットの場合、 --cacert は不要です。 --noproxy '' これは、curl がループバック ターゲットのプロキシをサイレントにバイパスしないことを保証します。

2 つの異なる TLS チェックがあります。

  • クライアントは、アダプターによって提示された証明書を検証します。アダプター CA とのクライアントの信頼を構成します。
  • アダプターは実際の上流サーバーを検証します。 tls.verifyUpstream デフォルトは true です。クライアント --cacert プライベートの起点 CA をアダプターに提供しません。

検証の無効化を証明書エラーの通常の修正として扱わないでください。所有されている自己署名フィクスチャの場合、 tls.verifyUpstream:false アダプター構成内の明示的な評価例外であり、その後に再起動が続きます。個別の上流チェックが弱体化します。参照 mitmproxy 証明書の動作.

デフォルトの Cookie の動作

ブラウザの Cookie を使用する そして 応答を保存 Set-Cookie 更新 はデフォルトでオンになっています。 User-Agent、Accept-Language、および Authorization はデフォルトでツール制御のままです。

ネイティブ リクエストの場合、Firefox はペアになったタブの Cookie ストアと一致するパーティションから URL に該当する Cookie を選択します。他のコンテナ/プライベート ストアはマージされません。ドメイン/パス/セキュア/有効期限ルールと同名パスの順序は引き続き関連します。値はネイティブ プロキシに提供されるので、ネイティブ プロキシは送信 Cookie ヘッダーを構築できます。したがって、削除されたブラウザーフェッチパスとは異なり、ネイティブヘルパーはメモリ内のセッションシークレットを処理します。

と cookies.mode:"replace"、空の場合も含め、ブラウザーの jar には権限があります。 jar から削除されたブラウザー Cookie は、その後の管理リクエストから削除されます。明示的に保護された名前と検出されたツールの変更が優先されます。と mode:"merge"、ブラウザで管理される名前が更新されている間、無関係なツールの Cookie が残ることがあります。

Response Set-Cookie フィールドは、サポートされている Domain/path/Secure/HttpOnly/SameSite/expiry/deletion/partition 属性を含む、Firefox の Cookie API を使用して、選択した同じストアに個別に適用されます。無効な Cookie は拒否できます。報告されたエラーを検査します。追加で構成されたオリジンは、ブラウザーの Cookie やブラウザー由来のヘッダーを受け取りません。

攻撃ペイロードを含むフィールドを保護する

ZAP テストを想定します session=ATTACK_PAYLOAD。その値をブラウザの有効なセッションに盲目的に置き換えると、テストが消去される可能性があります。逆に、すべてのリクエストで古い Cookie が保持されると、認証スキャンが役に立たなくなる可能性があります。

デフォルト 最初のリクエスト後にツールの Cookie/ヘッダーの変更を保持する クライアント接続/起点ごとのベースラインを記録し、その後の変更を保存します。最初に通常のシードリクエストを送信します。プロキシは最初のリクエストの意図を確実に推測することができず、新しい接続によって新しいベースラインが作成されます。このヒューリスティックは完全な保護ではありません。

予測可能なテストを行うには、次のメカニズムのいずれかを選択します。

  1. テストされている特定の Cookie/ヘッダー オーバーライドを無効にします。
  2. Cookie 名を追加する cookies.protectedNames またはヘッダーに headers.protectedNames.
  3. 選択したリクエストごとのアノテーションを送信します。

http X-Longshot-Preserve: cookie:session, User-Agent, Authorization

これにより、ツールの名前付き Cookie/ヘッダー フィールドが保持されます。 cookie 名前を指定しないと、完全なツールの Cookie ヘッダーが保存されます。

  1. そのリクエストのリクエスト側のオーバーライドをすべてバイパスします。

http X-Longshot-Override: off

アダプターは、転送する前にこれらの注釈ヘッダーを削除します。プロキシ認証、範囲、制限は引き続き適用されます。元のツールで注釈を構成します。これらをターゲット Web ページに配置することは、ブリッジ構成メカニズムではありません。

たとえば、 session protected を使用すると、ヘルパーが無関係の更新を継続できる間、ZAP が変更できるようになります。 preferences クッキー。徹底的な Cookie/認可/ユーザー エージェント テストの場合、これらのオーバーライドを無効にすると、変更検出ヒューリスティックへの依存が回避されます。

ブラウザ認証とその他のヘッダー

ブラウザ認証は、JSON 構成を通じてオプトインされます。これは、ブラウザーのソーシングを有効にした後にのみ、ペアになったターゲット タブによって実際のリクエストからキャプチャされます。これは、localStorage またはアプリケーション メモリ内のすべてのトークンを自動的に読み取るものではありません。観測値が存在する前に、後のブラウザー要求が必要になる場合があります。ブラウザーの認証をオフにすると、キャプチャされた値がヘルパーによって提供されなくなります。

ブラウザーの User-Agent または Accept-Language を選択すると、これらの HTTP フィールドのみが変更されます。ターゲット JavaScript の実行、本文 CSRF トークンの更新、ブラウザ TLS の再現、WAF の受け入れの保証は行いません。 IP/デバイスバインド認証と OAuth 更新には、引き続きアプリケーション ワークフローが必要です。

VHOST / ホスト処理

ネイティブ ヘルパーは、ツールの [ホスト] フィールドに内部ブリッジ エイリアスを置き換えません。承認された仮想ホスト テストに必要なホスト値をツールに送信させます。 HTTPS の場合、CONNECT 宛先は承認されたターゲットのままですが、ツールの Host ヘッダーは保持できます。

Host ヘッダーを変更しても、別のネットワーク宛先へのアクセスは許可されません。リバース プロキシは、それを別のアプリケーションにルーティングする場合があります。仮想ホストの動作を評価の承認に含めます。正確に不正なヘッダー バイトと競合するフレームは、この解析されたプロキシの外側にあります。

監査とプライバシー

ネイティブトラフィック リクエストのメタデータと変更/保護されたフィールド名を示します。監査では、Cookie/ヘッダーのシークレット値、クエリ値、および本文が省略されます。これは、プロキシがシークレットをまったく処理しないという意味ではなく、認証されたトラフィックを送信するためにシークレットを処理する必要があります。外部ツールは独自の履歴/結果を保持しており、それらの値が含まれる場合があります。

プライベート構成トークン、CA キー、およびデータ ディレクトリをレポート/ソース アーカイブから遠ざけてください。カスタム認証値を含む構成をダウンロードすると、それらの値を含むファイルを作成できます。

実行中のリクエストは終了する可能性があります。プロキシ クライアントは、ブロックされた作業に対してエラーを受け取ります。アダプターは、任意のツール プロセスを一時停止したり、そのリクエストを再実行したりしません。どのリクエストが成功したかを検査し、ツール独自の再試行/再開制御を使用します。再起動/再ペアリングするとトークンが変更され、ツール認証の更新が必要になります。

Tor とオニオン ルーティング

ブラウザベースの Longshot リクエストは、選択したブラウザのネットワークに従います。ネイティブ アダプターは別のプロセスであり、Firefox/Tor ブラウザーのプロキシ設定を継承しません。

SOCKS/トールは デフォルトではオフになっています ネイティブ構成で。承認されたオニオン評価の場合は、明示的に構成された既存の SOCKS サービスをリモート ホスト名解決で使用します。たとえば、それが実際にローカル Tor リスナーである場合は、次のようにオーバーライドします。

{
  "routing": {
    "socks5": "socks5h://127.0.0.1:9050"
  }
}

この例では、Tor を起動したり、ポート 9050 が存在することを確立したりしません。実際に構成されたサービスを選択します。 Tor ブラウザ インスタンスは別のリスナーを使用する場合があります。アダプターを再起動し、再度ペアリングします。 HTTP(S) upstream.url そして routing.socks5 相互に排他的です。

ネイティブ シムは SOCKS を通じてホスト名を解決し、サイレントな直接フォールバックはありません。明示的に構成されたアップストリーム/SOCKS ルートがないと、ダイレクト オニオン宛先はターゲット DNS の前で拒否されます。 SOCKS URL は、承認された SSH トンネルまたは他の SOCKS5 サービスを参照することもできます。これは本質的に Tor ルーティングを証明するものではありません。

Cookie 共有によって、ネイティブ ルートの出口 IP または TLS/ブラウザ フィンガープリントが Firefox と同一になるわけではありません。チャレンジまたはセッション バインディングによって拒否される可能性があります。ルートと予想されるセッションを個別に確認します。

エージェント API によって起動される分離されたネイティブ Nuclei は異なります。 内蔵リレーには Tor/SOCKS ルートがなく、システム DNS の前にオニオン ターゲットをブロックします。目的のブラウザで対象となるブラウザ側チェックを使用するか、ネイティブ プロキシ経由で個別に構成された外部ツールを使用します。 Nuclei チェックボックスが継承すると想定しないでください。 routing.socks5 ブラウザブリッジから。

実際の実行カバレッジの解釈

完全な WSTG リファレンス マップには、自動化されたサブセット、支援された作業、手動評価が含まれています。で 実際の入力カバレッジ:

  • 完了 入力が安全であるということではなく、実装されたルールがその入力上で終了したことを意味します。
  • 部分的 何らかの作業が実行されたものの、制限、中断、またはその他の条件により完了が妨げられたことを意味します。
  • スキップされました ルール/入力が実行されなかったことを意味します。理由を調べます。

WAF、ロールの不足、無効なセッション、非表示/未訪問のワークフロー、利用できないリクエスト本文、CSP、または予算の枯渇により、脆弱な入力がテストされないままになる可能性があります。ネイティブ プロキシ ペアリングでは、組み込みスキャナーからこれらの制限が削除されません。観察された CVE バージョン、ヘッダーの欠落、または異なる応答は、自動的にはエクスプロイトとはなりません。

リリース 2.18.1 は、ZIP/YAML CSP 検証と所有されている SQLite フィクスチャに対するネイティブ ZAP トラフィックを含む、192 の自動単体/回帰テスト、8 つの実際の Chrome チェック、および 8 つの実際の Firefox チェックに合格しました。公式ブラウザ ライブラリはバイトごとに検証されており、クリーンなソースの再構築により Firefox XPI が正確に再現されます。これらのテストは、名前付き実装の動作を検証します。すべての Juice Shop、WebGoat、bWAPP、または NodeGoat チャレンジの検出は示されていません。外部 ZAP SQLi の結果は、すべての脆弱性にわたる Longshot のリコールではなく、プロキシ パスを検証します。

ブラウザストレージとオプションのセッションファイル

ブラウザのストレージは、どちらのローカル ブリッジからも独立してアクティブなままになります。プロファイルごとの履歴、調査結果、レビュー、インベントリ、オプションが保存されます。レスポンスボディはベストエフォートの編集で保持できます。ブラウザで観察されるトラフィックには、キャプチャされた本文のないメタデータが含まれることがよくあります。

自動ファイル チェックポイントの場合:

  1. 登録・接続 エージェントAPIブラウザブリッジだけではありません。
  2. 開く 設定 → 評価セッション → 指示.
  3. 絶対値を入力してください セッションフォルダー エージェント API コンピューター上。
  4. 有効にする セッションファイルを自動的に保存する そして選択してください セッション設定を保存する.
  5. 使用する 今すぐセッションを保存 即時のチェックポイントの場合。通常の変更も保存をトリガーします。
  6. 使用する 現在のセッションをエクスポートする / セッションファイルをインポートする 手動転送の場合。手動インポートにはネイティブ ホストは必要ありません。

ファイルは安定したプロファイル ID を使用します。 .longshot.json、1 つのオリジンに対して明示的なプロファイルを許可します。これらは読み取り可能な暗号化されていない評価アーカイブであり、アプリケーション データ、作成されたテンプレート、および保持された本体を含めることができます。ブラウザ管理の Cookie、プロバイダー トークン、実行許可は除外されます。

書き込みはアトミックなプライベート ファイル チェックポイントです。突然終了した場合、最後に完了した保存内容のみを復元できます。復元された実行中のスキャンは中断されます。ブリッジが切断された場合、ブラウザの保存は続行され、ファイルの保存は待機します。未解決の有効なチェックポイントでは、ターゲットを切り替える前に再接続するか、ファイル保存を無効にする必要がある場合があります。セッション ファイルの最大サイズは 256 MB で、明示的なエラーが発生します。

評価アーカイブのエクスポートは異なります 構成をダウンロードする ブラウザブリッジで。前者は評価の証拠/オプションを保存します。後者はネイティブ プロキシ設定を保存します。
