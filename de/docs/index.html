Longshot 2.18.1 — Anleitung und Funktionsübersicht

Aktualisiert am 10. November 2026 für Longshot 2.18.1 (Firefox- und Chrome-Editionen) und seine nativer HTTP/HTTPS-Tool-Proxy. Dies ersetzt das allgemeine 2.11.1-Tutorial. Die folgenden Anweisungen beschreiben die ausgelieferte Implementierung, einschließlich ihrer Grenzen. Ältere Bridge-Beispiele sind mit dieser Version nicht austauschbar.

Longshot ist eine Browser-Sitzungs-Workbench für die autorisierte Bewertung von Webanwendungen. Es kombiniert Erkennung, einen eigenen aktiven JavaScript-Scanner, manuelle HTTP-Tools, importierte Vorlagen, Ergebnisüberprüfung und Berichte. Mit der optionalen Browser Bridge können externe Tools ausgewählte Firefox-Sitzungswerte verwenden und gleichzeitig ihre eigenen nativen HTTP-Anfragen senden.

Ein nützlicher erster Durchgang ist: Öffnen Sie die Anwendung → Anmelden → Starten Sie Longshot über diese Registerkarte → Verbinden → Validieren Sie die Sitzung → Entdecken Sie Eingaben → Führen Sie ausgewählte Prüfungen durch → Überprüfen Sie Beweise.

Verarbeitet Ihre Anwendung sensible Nutzerdaten oder Geld, lassen Sie sie von einem Cybersicherheitsteam professionell prüfen. Das gilt auch für mit KI entwickelte Apps. Ein Erweiterungsscan ersetzt weder Berechtigungsprüfungen noch die Prüfung der Geschäftslogik oder eine unabhängige Sicherheitsbewertung. Keine gefundenen Schwachstellen bedeuten nicht automatisch, dass die App sicher ist.

In diesem Dokument werden Befehle erläutert. Durch die Aktualisierung wird keine Software installiert, kein Host registriert, keine Browsereinstellungen geändert oder Scans ausgeführt. Führen Sie Beispiele nur anhand Ihres autorisierten Bewertungsziels durch. Die Probe http://localhost:8080 ist ein lokales Zielbeispiel, kein integrierter Longshot-Dienst.

Stellen Sie sich Folgendes vor: Ihre App wird live geschaltet, ein Angreifer findet den Fehler und ein Benutzer eröffnet sein Konto mit einem Kontostand von Null. Ihr ganzes Geld – weg.

Der Code sah überzeugend aus. Die KI sagte, es sah sicher aus. Das war nicht genug.

Sprachmodelle liefern nicht immer dieselben Antworten. Sie können Schwachstellen übersehen und trotzdem sehr überzeugend klingen. Holen Sie eine zweite Einschätzung ein — mit Longshot.

Longshot verwandelt Firefox in eine Sicherheitswerkbank für die von Ihnen erstellten Web-Apps. Führen Sie wiederholbare Prüfungen für die tatsächlich ausgeführte Anwendung durch, überprüfen Sie die HTTP-Beweise und untersuchen Sie die Schwachstellen, bevor Ihre Benutzer den Preis zahlen.

Scheckschutz wird unterstützt SQL/NoSQL-Injection, serverseitige Code- und Template-Injection, reflektierte XSS-Kandidaten, Path Traversal/File Inclusion, offene Weiterleitungen und CRLF/Header-Injection, mit optionaler Live-DOM-XSS-Überprüfung. Rezension schwache Sicherheitsheader, Cookie- und CORS-Richtlinien, offengelegte Konfiguration und Fehleroffenlegung, mit optionalen Prüfungen für weitere Angriffsklassen.

Beginnen Sie mit der Browser-Registerkarte, die Sie bereits verwenden. Behalten Sie Live-Cookies bei, konfigurieren Sie die Sitzungsvalidierung, stellen Sie sie nach einem Sitzungsverlust wieder her und halten Sie die Einstellungen, den Verlauf und die Ergebnisse jedes Ziels organisiert.

Lassen Sie die KI arbeiten — und prüfen Sie das Ergebnis. Verbinden Sie einen Agenten über MCP, um autorisierte Prüfungen durchzuführen und Ergebnisse zu untersuchen. Verwenden Sie die native Browser Bridge, um ZAP, sqlmap, curl, ffuf oder wget in die verbundene Browsersitzung einzubinden, ohne Cookie-Werte manuell zu kopieren. Die Tools senden ihre eigenen HTTP-Anfragen und Payloads; Browser-Cookie-Überschreibungen sind standardmäßig aktiviert und können deaktiviert werden.

Fortgeschrittene Benutzer können kompatible importieren CVE-Vorlagen und korrelieren OAST-Rückrufe mit den Sonden, die sie verursacht haben. Überprüfen und protokollieren Sie Ihre Urteile und exportieren Sie dann beweiskräftige Informationen HTML-, JSON-, CSV- oder SARIF-Berichte, mit Druck-/PDF-Ausgabe. Erklären Sie die Ergebnisse mit dem Filmbetrachter, einschließlich Live-CSS/JavaScript-Seitenkontext, animierte 3D-Elemente, Pause und Vollbild-Steuerelemente. Wählen Sie ein ansprechendes Thema und passen Sie Bewegung und Ton an Ihren Arbeitsplatz an.

Veröffentlichungshinweise

Die Geschichte des Kontoverlusts ist hypothetisch, keine Behauptung über einen echten Kunden oder eine Garantie, dass Longshot finanzielle Verluste verhindert. Die Erweiterung führt Bewertungen durch, keine kontinuierliche Angriffsblockierung. Feststellungen bedürfen einer Überprüfung; In der Abdeckungstabelle werden begrenzte Unterstützung und Lücken erläutert, die nur manuell verfügbar sind. Die DOM-Analyse umfasst Indikatoren und unterstützte Ausführungskanarien, keine universelle DOM-Exploit-Abdeckung. Die Filmsequenz erklärt Beweise; es fügt keinen Ausbeutungsbeweis hinzu.

MCP und Browser Bridge müssen lokal eingerichtet werden. Der native Tool-Proxy verwendet einen separaten Node/Python/mitmproxy-Prozess und das Abfangen von HTTPS erfordert die Vertrauenskonfiguration des Tools für die Adapter-CA. Es handelt sich um einen analysierten HTTP-Transport, nicht um bytetransparentes Roh-TCP. Cookie-Überschreibungen können deaktiviert werden; Ein Browser-Cookie oder User-Agent garantiert keine browseridentische Vernetzung oder WAF-Akzeptanz. Externes ZAP bleibt separat installiert. Die Ausführung der Vorlage hängt von der Kompatibilität/Laufzeit ab; OAST erfordert einen konfigurierten Anbieter. Für die Authentifizierungsvalidierung ist ein aussagekräftiger geschützter Endpunkt/Marker erforderlich. Zielprofile trennen Bewertungsdaten; Der Tab/Container stellt die Cookie-Sitzung bereit.

Stellen Sie für Anwendungen, die sensible Daten oder Geld verarbeiten, ein Cybersicherheitsteam ein und nutzen Sie Longshot als einen Teil der Bewertung. Verwenden Sie es nur für Anwendungen, die Sie besitzen oder zum Testen berechtigt sind.

Installieren Sie die Chrome-Edition

  1. Laden Sie die herunter Chrome ZIP von den Veröffentlichungslinks oben/unten und extrahieren Sie es in einen Ordner, den Sie behalten.
  2. Offen chrome://extensions, aktivieren Entwicklermodus, auswählen Ausgepackt laden, und wählen Sie dann den extrahierten Ordner aus, der Folgendes enthält manifest.json.
  3. Öffnen Sie Ihre autorisierte Anwendung, melden Sie sich an, starten Sie Longshot über diese Registerkarte und stellen Sie eine Verbindung her.
  4. Lassen Sie die Workbench-Registerkarte während des Scannens und der nativen Kopplung geöffnet. Durch das Schließen wird die aktive Arbeit am Motor beendet; Gespeicherte Beweise bleiben erhalten und werden wiederhergestellt, ohne dass unsichere Anfragen erneut abgespielt werden müssen.
  5. Verwenden Sie für den Start des nativen Tool-Proxys den genauen Ursprung, der von Chrome angezeigt wird, z chrome-extension://YOUR_INSTALLED_ID, rather than a Firefox moz-extension:// Herkunft. Der Proxy verwendet echte Ziel-URLs; Es ist kein Eintrag in der Hosts-Datei erforderlich.

Chrome Agent API/MCP-Registrierung

Aus dem beibehaltenen vollständigen Quellcode-Checkout, nach der Installation der angehefteten Hilfsabhängigkeit:

npm --prefix native-bridge ci --omit=dev
node bridge/bin/longshot-bridge install --browser chrome \
  --extension-id YOUR_INSTALLED_32_LETTER_ID \
  --port 8775 --data-dir /absolute/private/longshot-chrome
node bridge/bin/longshot-bridge mcp \
  --port 8775 --data-dir /absolute/private/longshot-chrome

Zur Verwendung mit Chrom --browser chromium. Verwenden Sie die tatsächliche ID in chrome://extensions; Registrieren Sie sich erneut, wenn die Installation der Store-Edition eine andere ID ergibt. Das separate Port-/Datenverzeichnis vermeidet eine Kollision mit einem Firefox-Host. Diese Agent-API unterscheidet sich vom HTTP-Tool-Proxy (Standardports 8900/8901). Linux ist die getestete Native-Host-Plattform; Die macOS-Registrierung ist implementiert, aber hier nicht getestet, und es wird kein Windows-Native-Host-Installationsprogramm bereitgestellt.

Eine detaillierte Browser Bridge-Konfiguration ist auch in den Erweiterungen verfügbar Browser Bridge → Informationen Dialog. Der integrierte Scanner verwendet die entsprechenden Browser-Cookies der gebundenen Registerkarte, einschließlich HttpOnly-Cookies. Firefox wählt Cookies nach URL, Pfad, Sicherheitsattributen und Cookie-Speicher aus. Die geschützten Cookie-/Autorisierungs-/Hostfelder des Scanners sind keine gewöhnlichen bearbeitbaren Fuzz-Eingaben.

Profile und Konten

Ziele trennt Verlauf, Ergebnisse, Anforderungsjournal, erkannte Endpunkte, Überprüfungen und Scankonfiguration. Durch die Rückkehr zu einem Profil werden Bewertungsdaten wiederhergestellt, nicht eine alte authentifizierte Browsersitzung. Explizite Profile können einen gemeinsamen Ursprung haben.

Normalerweise teilen sich zwei normale Firefox-Registerkarten Cookies. Verwenden Sie unabhängige Container oder einen separaten privaten Cookie-Speicher für wirklich unterschiedliche Testidentitäten. Beim Wechseln des Profils wird keine zweite Kontositzung erstellt. Der Vergleich in Sitzung B erfordert denselben Zielursprung und einen separaten Speicher.

Leichte Entdeckung und ein fokussierter aktiver Scan

Erster Durchgang: Entdeckung und passive Überprüfung

  1. Set Anfragen pro Sekunde auf 0,5–1, Crawling-Tiefe auf 1 und maximal erkannte URLs auf 25–50.
  2. Geh Maximaler Befund, Aggressiv, CVE-Autophase, OAST und native Ausführung aus.
  3. Set Auto-Fuzz → Aus. Lassen Sie Seitenklicks/Scroll- und Live-DOM-/Timing-/Callback-Tests deaktiviert.
  4. Wählen Sie die passiven Übersichtsgruppen aus: Header, Cookies, Offenlegung, Formulare, DOM-Quellen-/Senkenüberprüfung und CORS.
  5. Wählen Sie Nur Spinne und beginnen.
  6. Inspizieren Sitemap, HTTP-Verlauf, API-Explorer, Server-Stack und Erkenntnisse.

Spider folgt entdeckten Links/Formularen im Gültigkeitsbereich, ohne Formularschreibvorgänge abzusenden. Es kennt nicht jeden versteckten Endpunkt. GET-Anfragen können weiterhin anwendungsspezifische Nebenwirkungen haben; „Lesemethode“ legt kein nebenwirkungsfreies Ziel fest.

Zweiter Durchgang: eine begrenzte aktive Bewertung

  1. Behalten Auto-Fuzz → Aus um die separate Überprüfung der integrierten aktiven Regeln zu erleichtern.
  2. Wählen Sie die relevanten aktiven Übersichtsprüfungen aus, z. B. SQL-Injection und Reflected XSS.
  3. Verwenden Sie kleine Limits, zum Beispiel 150 aktive Anfragen, 10 aktive URLs und fünf aktive Parameter.
  4. Wählen Sie Nur aktive Schecks um die aktuelle Seite und das gespeicherte Inventar wiederzuverwenden, oder Spinne + aktive Kontrollen erst einmal entdecken.
  5. Starten Sie, überprüfen Sie alle erforderlichen Genehmigungen und beobachten Sie die Anzahl der Aktivitäten und Anfragen.
  6. Überprüfen Sie die Anfrage, den Ausgangswert, die wiederholten Untersuchungs-/Kontrollbeweise, das Urteil und das Vertrauen jedes Ergebnisses.
  7. Offen WSTG-Prüfungen → Tatsächliche Eingabeabdeckung um abgeschlossene, teilweise und übersprungene Arbeiten anzuzeigen.

„Auto-Fuzz Off“ schaltet aktive Prüfungen nicht aus. SQLi/XSS/SSTI und andere dedizierte Regeln generieren ihre eigenen Sonden. Umgekehrt führt das Ankreuzen einer aktiven Regel nicht zu einer fehlenden Eingabe und führt auch nicht dazu, dass ein reiner Spider-Lauf die generische aktive Phase ausführt.

Aggressive Optionen und Laufgenehmigung

Aggressiv ermöglicht explizit genehmigte Methoden/Fähigkeiten; Es führt nicht jede Prüfung durch und garantiert keine stärkeren Beweise.

  1. Ermitteln Sie zunächst Eingaben und validieren Sie die Authentifizierung.
  2. Aktivieren Sie nur die benötigten erweiterten Optionen und Schreib-/Hochlade-/Löschberechtigungen.
  3. Scanoptionen speichern.
  4. Wählen Sie Überprüfen/genehmigen Sie den nächsten aggressiven Lauf.
  5. Überprüfen Sie das Ziel, die Funktionen, die Methodenberechtigungen und die Budgets.
  6. Klicken Sie Genehmigen Sie diesen nächsten Lauf. Diese Benutzeraktion fordert alle fehlenden kombinierten Firefox-Berechtigungen an und erstellt die Gewährung für die nächste Ausführung.
  7. Starten Sie den Lauf mit der überprüften Konfiguration.

Der Zuschuss ist einmalig, läuft nach 30 Minuten ab und wird durch relevante Ziel-/Konfigurations-/Anfrageeinstellungsänderungen ungültig. Für einen neuen Scan ist normalerweise eine neue Bewilligung erforderlich. Das Speichern nicht abgeschlossener Optionen ist zulässig. Beim Starten oder Genehmigen werden erforderliche Felder validiert.

Firefox erfordert permissions.request() direkt aus einer echten Benutzeraktion hervorgehen. Das Ändern einer Einstellung ist kein Grund, im Hintergrund willkürliche Berechtigungen zu erteilen. Wenn die Berechtigung verweigert wird, überprüfen Sie die genaue Funktion, versuchen Sie es über die Genehmigungsschaltfläche erneut oder deaktivieren Sie diese Funktion. Normale Betriebssystem-/Browser-Berechtigungsaufforderungen bleiben außerhalb der Erweiterungs-DOM-Automatisierung.

Maximaler Befund ist eine breite Voreinstellung

Diese Voreinstellung aktiviert viele Phasen, einschließlich erweiterter Überprüfung, OAST- und Session-B-Vergleich, und erweitert mehrere Budgets. Es handelt sich nicht um einen „Alles finden“-Schalter. Es wird kein OAST-Konto erstellt, keine Anbieter-URL/Callback-Domäne ausgefüllt, keine gültige Sitzung B ausgewählt, Nuclei installiert oder fehlende Rollen authentifiziert.

Wenn die Genehmigung leere OAST-Felder oder fehlende Sitzung B meldet, konfigurieren Sie diese oder schalten Sie diese Optionen aus. Dies ist unabhängig davon, ob die Ziel-URL gültig ist.

Zwei Befehlsinjektionssteuerungen

Übersicht → OS-Befehlsanzeigen ermöglicht direkte Unix-orientierte Befehlsausgabe-Probes. Es ist standardmäßig deaktiviert. Überprüfen Sie die Autorisierungsanforderungen für die tatsächliche Ausführung.

Auto-Fuzz erkennt Eingaben

Benutzen Vorschau der erkannten Eingaben zuerst. Es liest gespeicherte Bestände und meldet berechtigte/übersprungene Anfragen, ohne Proben zu senden. Auto-Fuzz benötigt nicht die URL-/Parameterfelder des manuellen Fuzzers. Durchsuchen oder durchsuchen Sie zuerst, wenn das Inventar leer ist.

Wählen Sie Nutzlastklassen aus und wählen Sie die separate aus Auto-fuzz Taste. Erkannte Anforderungstexte einbeziehen startet und erfordert Aggressiv plus Genehmigung für den nächsten Lauf. Tokengebundene Formulare, nicht unterstützte Methoden, nicht verfügbare Körper und XML werden von dieser automatischen Eingabeauswahl übersprungen. Bestehende Ausschlüsse, Anforderungslimits und Drosselungsverhalten gelten weiterhin.

Verfügbare Klassen-Kontrollkästchen sind SQLI, NOSQLI, CODE, XSS, SSTI, TRAVERSAL, COMMAND, SSRF, REDIRECT, CRLF und CUSTOM. Neue Standardeinstellungen ermöglichen SQLI, SSTI, TRAVERSAL, REDIRECT und CRLF. Die generische Schleife überspringt SSRF; verwenden SSRF-Kanarienvögel / Rückrufe für die durchgeführte Verifizierung. CUSTOM verwendet eingegebene/aktivierte benutzerdefinierte Werte und meldet Antwortunterschiede mit geringer Konfidenz, es sei denn, ein dedizierter Matcher stellt weitere fest.

Warum die Probe-Bibliothek hierher gehört

Die Bibliothek liefert Nutzlastwerte und überprüfte Vorlagen; Die Fuzzer-Steuerung wählt aus wohin und wie man sie verschickt. Es ersetzt nicht die manuelle URL/den manuellen Parameter. Die Optionen der gemeinsam genutzten Bibliothek wirken sich auch auf den aktiven Scan und die automatischen Phasen nach dem Speichern aus.

Server-Stack und Smart-Analysator

Benutzen Software erkennen um unterstützte Beobachtungen zu sammeln. Durchsuchen Sie repräsentative Seiten und behalten Sie die passenden Antworten bei, wenn Sie Körperbeweise benötigen. Dann wählen Sie Analysieren Sie aufgezeichnete Beweise für eine lokale passive Korrelation von bis zu 200 zuletzt gespeicherten Antworten. Der Analysator selbst fügt keine Zielanforderungen hinzu.

Die Ansicht trennt Browserkomponenten, WAF/CDN/Edge, Webserver/Reverse-Proxy und Anwendungs-/Laufzeitsignale. Mögliche Konfigurationskarten erläutern deren Nachweis und schlagen eine Verifizierung vor. Es handelt sich um Hypothesen: Browserantworten können die Ursprungs-IP, private Subnetze, Backend-Datenbankeinstellungen, TLS-Beendigung, Firewall-Regeln oder Proxy-Vertrauenslisten nicht genau ermitteln. OAST-Aufbau und Interpretation

OAST beobachtet DNS/HTTP-Interaktionen, die durch eine Sonde verursacht werden, wenn die normale Antwort das Verhalten nicht offenbart. Longshot besitzt seine Registrierungs-/Korrelationsschlüssel; Ein zufälliger, vorab generierter Rückruf von einem anderen Client ist nicht austauschbar.

  1. Wählen Sie einen Interactsh-kompatiblen Dienst, den Sie kontrollieren oder zu dessen Nutzung Sie berechtigt sind.
  2. Treten Sie ein Anbieter-URL: die vollständige API-Basisadresse des Anbieters, normalerweise HTTPS. HTTP ist nur für Loopback-Anbieter zulässig.
  3. Geben Sie die Übereinstimmung ein Rückrufdomäne ohne http://, ein Hafen oder ein Pfad.
  4. Treten Sie ein Anbieter-Token nur, wenn dieser Anbieter dies verlangt.
  5. TTL und Poll-Intervall festlegen; Aktivieren Sie OAST und die relevanten SSRF/XXE/Log4Shell/Befehlsoptionen.
  6. Benutzen Testen Sie die OAST-Verbindung um die Registrierung/Abstimmung zu überprüfen.
  7. Benutzen Testen Sie den OAST-Rückruf um einen separaten korrelierten Kanarienvogel von diesem Browser aus zu senden.
  8. Speichern, überprüfen und genehmigen Sie den tatsächlichen Scan. Überprüfen Sie die genaue Korrelation und das Protokoll bei OAST-Interaktionen.

Wenn Sie beispielsweise den passenden öffentlichen Dienst unter nutzen https://oast.pro, seine Rückrufbasis ist oast.pro. Dies ist ein Beispiel, keine Verfügbarkeitsgarantie oder eine Verpflichtung zur Nutzung dieses Anbieters. Ein selbst gehosteter Anbieter benötigt eine eigene ordnungsgemäß delegierte erreichbare Domäne, DNS/Listener und TLS; Ein Laptop-HTTP-Listener allein ist kein öffentlicher Rückrufdienst. Folgen Sie offizielles Interactsh-Setup.

Eine DNS-Auflösung kann von einem Vermittler/Sicherheitsdienst stammen. Ein Rückruf allein beweist keinen willkürlichen internen Zugriff, Datendiebstahl oder Codeausführung. Die separate isolierte Nuclei-Engine verfügt über eine eigene native Interactsh-Registrierung. Bei diesen Ereignissen handelt es sich nicht um die Registrierung des Browser-Clients.

Der browserseitige OAST-Client erfordert keine Go-, Node- oder Agent-API. Zu den Release-Tests gehörten die Registrierung am offiziellen Server, der Abruf verschlüsselter HTTP-Rückrufe und die Korrelation beim Loopback. Sie haben weder die Verfügbarkeit des öffentlichen Anbieters noch den ausgehenden Datenverkehr Ihres Zielservers festgestellt. Zum normalen, korrekt delegierten OAST-Setup gehört keine Bearbeitung der Hosts-Datei.

Browser Bridge: nativer Tool-Proxy

Was es sendet

Ein externes Tool generiert die Anfrage, einschließlich der Angriffsnutzlast, der Methode, des Hauptteils und der Abfrage. Der native Adapter leitet es über mitmproxy weiter und wendet nur konfigurierte Cookie-/Header-Änderungen an. Das tut es nicht Bitten Sie Firefox, den Abruf im Auftrag von ZAP oder einem anderen Tool durchzuführen.

Dadurch bleiben die native HTTP-Semantik und die Nutzdatengenerierung des Tools erhalten, jedoch keine willkürlichen Original-Wire-Bytes: mitmproxy analysiert/serialisiert HTTP und stellt eine eigene ausgehende TLS-Verbindung her. Eine Browser-User-Agent-Zeichenfolge sorgt nicht dafür, dass der native TLS-/Netzwerk-Fingerabdruck mit dem von Firefox identisch ist.

Installieren Sie den heruntergeladenen Adapter

  1. Offen Browser-Bridge. Nur Nativer Tool-Proxy ist in 2.18.1 verfügbar.
  2. Wählen Sie Laden Sie den nativen Adapter herunter und extrahieren Sie es.
  3. Geben Sie das extrahierte ein native-bridge Verzeichnis. Es enthält cli.js, bootstrap.py, config.json und der gebündelte Node ws Abhängigkeit.
  4. Installieren Sie Node.js 20+ und Python 3.12+, falls diese noch nicht verfügbar sind.
  5. Führen Sie das einmalige Python-Setup aus:

sh cd /absolute/path/to/native-bridge python3 bootstrap.py

Dadurch entsteht ein lokaler .venv und installiert angehefteten mitmproxy 12.2.3. Für die Installation ist ein Internetzugang erforderlich. Beim normalen Start werden weder Scannercode noch Payload-Listen heruntergeladen.

  1. Verwenden Sie den angezeigten Befehl dein Erweiterungsseite:

sh node cli.js --config config.json \ --extension-origin moz-extension://YOUR-LONGSHOT-UUID

Ersetzen Sie den Platzhalter durch den vollständigen aktuellen Erweiterungsursprung. Es handelt sich nicht um die Zielwebsite, Add-on-ID oder einen von einem anderen Firefox-Profil kopierten Ursprung.

  1. Lassen Sie das Terminal laufen. Nachdem der Proxy-Listener bereit ist, druckt er die Proxy-Adresse, den Steuerport, das neue Pairing/Proxy-Token und den CA-Zertifikatspfad.

Wenn Sie aus der Quell-ZIP-Datei entwickeln, anstatt das gebündelte Adapterarchiv zu verwenden, installieren Sie zuerst die angeheftete Knotenabhängigkeit, falls diese nicht vorhanden ist:

cd native-bridge
python3 bootstrap.py

--mitmdump /absolute/path/to/mitmdump oder LONGSHOT_MITMDUMP wählt eine vorhandene Laufzeit aus. --data-dir /absolute/private/run-directory wählt das CA/audit-Verzeichnis aus; Die Standardeinstellung ist run innerhalb des nativen Adapters. Strg+C stoppt den Adapter.

Der manuelle native Proxy ist von der Agent-API-Hostregistrierung getrennt. Es braucht nicht node bridge/bin/longshot-bridge install lediglich als Proxy für Curl/ZAP. Linux/Firefox wurde in Release-Integrationstests getestet; Schließen Sie aus diesem manuellen Node/Python-Startpfad nicht die Unterstützung des Installationsprogramms für native Nachrichten auf einer anderen Plattform ab.

  2. Überprüfen Sie die angezeigte Herkunft und den Cookie-Speicher. Benutzen Registerkarten aktualisieren ggf.
  3. Treten Sie ein Steueranschluss 8901, sofern nicht in der Adapterkonfiguration geändert.
  4. Fügen Sie den aktuellen ein Pairing-/Proxy-Token vom laufenden Adapter.
  5. Wählen Sie Koppeln Sie die native Bridge und überprüfen Sie den Bereitschaftsstatus.

Das Feld löscht das Token nach erfolgreicher Kopplung. Ein Neustart erzeugt ein neues Token: Paaren Sie es erneut und aktualisieren Sie die Proxy-Anmeldeinformationen in jedem externen Tool. Der Proxy-Port 8900 ist für Werkzeuge; Der Steueranschluss 8901 ist für Firefox. Keiner von beiden verwendet das Agent-API-Bearer-Token von Port 8765.

Tatsächliche Ziel-URLs und Bridge.invalid

Verwenden Sie die echte Adresse, z http://localhost:8080/search?q=apple, in Ihrem Tool. Wenn Sie HTTPS testen, verwenden Sie das echte https://... Adresse. Die eigene Adresse des Proxys bleibt erhalten http://127.0.0.1:8900 denn das ist der lokale HTTP-Proxy-Listener, auch für HTTPS CONNECT.

Nein /etc/hosts Eintrag erforderlich. Das Alte bridge.invalid Die Adresse war ein adapterspezifischer Alias zum Zuordnen der HTTP-URL eines Dienstprogramms zu einem ausgewählten Browser-Abrufziel. Der aktuelle native Proxy unterstützt tatsächliche Ziel-URLs und HTTPS CONNECT, sodass eine Zuordnung nicht erforderlich ist.

localhost ist kein austauschbarer Alias für jedes Ziel: Er benennt den lokalen Computer aus der Netzwerkumgebung des relevanten Prozesses. Es ist nur dann korrekt, wenn das Ziel tatsächlich an diesem Ursprung lokal ist. Ein anderer Hostname kann einen anderen virtuellen Host, eine andere Cookie-Richtlinie oder einen anderen Ursprung auswählen, selbst wenn beide Namen in dieselbe IP aufgelöst werden.

Ein vorhandener veralteter Host-Eintrag ist für den neuen Workflow irrelevant; Verwenden Sie es nicht in Tool-URLs. Bei der Vorbereitung dieses Tutorials wurden keine Änderungen an der Hosts-Datei vorgenommen.

HTTPS-Vertrauen

Der Adapter generiert seine eigene lokale CA unter dem ausgewählten Datenverzeichnis, normalerweise:

run/ca/mitmproxy-ca-cert.pem       public CA certificate for tool trust
run/ca/mitmproxy-ca.pem            sensitive CA material/private key

Konfigurieren Sie die Konfiguration der Bewertungsvertrauensstellung des externen Tools mit dem öffentlichen Zertifikatspfad, der beim Start gedruckt wird. Geben Sie den privaten Schlüssel nicht weiter und gehen Sie nicht davon aus, dass der System-/Firefox-Vertrauensspeicher geändert wurde. Der Adapter installiert seine Zertifizierungsstelle nicht in einem der Truststores.

Für Locken:

curl --noproxy '' \
  --proxy http://127.0.0.1:8900 \
  --proxy-user 'bridge:CURRENT_TOKEN' \
  --cacert /absolute/path/to/native-bridge/run/ca/mitmproxy-ca-cert.pem \
  'https://actual-target.example/search?q=apple'

Ersetzen CURRENT_TOKEN und den Ziel-/Zertifikatpfad. Für ein reines HTTP-lokales Ziel: --cacert ist unnötig. --noproxy '' stellt sicher, dass Curl den Proxy für ein Loopback-Ziel nicht stillschweigend umgeht.

Es gibt zwei unterschiedliche TLS-Prüfungen:

  • Der Client überprüft das vom Adapter vorgelegte Zertifikat. Konfigurieren Sie die Vertrauensstellung des Clients mit der Adapter-CA.
  • Der Adapter überprüft den echten Upstream-Server. tls.verifyUpstream Standardmäßig wahr. Kunde --cacert stellt dem Adapter keine private Ursprungszertifizierungsstelle bereit.

Betrachten Sie die Deaktivierung der Überprüfung nicht als normale Lösung für Zertifikatsfehler. Für ein eigenes, selbstsigniertes Gerät, tls.verifyUpstream:false ist eine explizite Bewertungsausnahme in der Adapterkonfiguration, gefolgt von einem Neustart; es schwächt diese separate Upstream-Prüfung. Siehe Verhalten des Mitmproxy-Zertifikats.

Cookie- und Header-Überschreibungen ohne Beschädigung der Sonden

Standardmäßiges Cookie-Verhalten

Verwenden Sie Browser-Cookies und Antwort speichern Set-Cookie-Updates sind standardmäßig aktiviert. User-Agent, Accept-Language und Autorisierung bleiben standardmäßig vom Tool gesteuert.

Für eine native Anfrage wählt Firefox geeignete Cookies für die URL aus dem Cookie-Speicher des gekoppelten Tabs und der entsprechenden Partition aus. Andere Container/Privatgeschäfte werden nicht zusammengelegt. Domänen-/Pfad-/Sicherheits-/Ablaufregeln und die Reihenfolge der gleichnamigen Pfade bleiben weiterhin relevant. Dem nativen Proxy werden Werte bereitgestellt, damit dieser den ausgehenden Cookie-Header erstellen kann. Im Gegensatz zum entfernten Browser-Abrufpfad verarbeitet der native Helfer daher Sitzungsgeheimnisse im Speicher.

Mit cookies.mode:"replace", ist die Browser-JAR-Datei maßgeblich, auch wenn sie leer ist. Ein aus dem JAR gelöschtes Browser-Cookie wird aus späteren verwalteten Anfragen entfernt. Explizit geschützte Namen und erkannte Werkzeugänderungen haben Vorrang. Mit mode:"merge"Nicht verwandte Tool-Cookies können bestehen bleiben, während vom Browser verwaltete Namen aktualisiert werden.

Antwortsatz-Cookie-Felder werden mithilfe der Cookie-API von Firefox einzeln auf denselben ausgewählten Speicher angewendet, einschließlich der unterstützten Domain-/Pfad-/Secure-/HttpOnly-/SameSite-/Expiry-/Deletion-/Partitionsattribute. Ungültige Cookies können abgelehnt werden; Überprüfen Sie gemeldete Fehler. Zusätzlich konfigurierte Ursprünge empfangen keine Browser-Cookies oder vom Browser abgeleiteten Header.

Schützen Sie Felder, die Angriffsnutzlasten enthalten

Nehmen wir ZAP-Tests session=ATTACK_PAYLOAD. Das blinde Ersetzen dieses Werts durch die gültige Sitzung des Browsers könnte den Test zerstören. Umgekehrt könnte die Beibehaltung eines veralteten Cookies in jeder Anfrage dazu führen, dass ein authentifizierter Scan unbrauchbar wird.

Die Standardeinstellung Behalten Sie die Cookie-/Header-Änderungen des Tools nach der ersten Anfrage bei zeichnet eine Baseline pro Client-Verbindung/Herkunft auf und behält nachfolgende Änderungen bei. Senden Sie zunächst eine gewöhnliche Samenanfrage. Der Proxy kann bei der ersten Anfrage nicht zuverlässig auf die Absicht schließen und eine neue Verbindung erstellt eine neue Baseline. Diese Heuristik bietet keinen vollständigen Schutz.

Wählen Sie für vorhersehbare Tests einen dieser Mechanismen:

  1. Deaktivieren Sie die jeweilige Cookie-/Header-Überschreibung, die getestet wird.
  2. Fügen Sie Cookie-Namen hinzu cookies.protectedNames oder Header zu headers.protectedNames.
  3. Senden Sie eine selektive Anmerkung pro Anfrage:

http X-Longshot-Preserve: cookie:session, User-Agent, Authorization

Dadurch bleiben die benannten Cookie-/Header-Felder des Tools erhalten. cookie Ohne Namen bleibt der gesamte Tool-Cookie-Header erhalten.

  1. Alle anforderungsseitigen Außerkraftsetzungen für diese Anforderung umgehen:

http X-Longshot-Override: off

Der Adapter entfernt diese Anmerkungsheader vor der Weiterleitung. Es gelten weiterhin die Proxy-Authentifizierung, der Umfang und die Beschränkungen. Konfigurieren Sie Anmerkungen im ursprünglichen Tool. Das Einfügen in eine Zielwebseite ist kein Bridge-Konfigurationsmechanismus.

Zum Beispiel behalten session protected lässt ZAP es variieren, während der Helfer mit der Aktualisierung einer nicht verwandten Datei fortfahren kann preferences Keks. Für umfassende Cookie-/Autorisierungs-/User-Agent-Tests vermeidet die Deaktivierung dieser Außerkraftsetzungen die Abhängigkeit von Heuristiken zur Änderungserkennung.

Browserautorisierung und andere Header

Die Browserautorisierung erfolgt über die JSON-Konfiguration. It is captured from an actual request by the paired target tab only after enabling browser sourcing. It is not an automatic reader for every token in localStorage or application memory. Möglicherweise ist eine spätere Browseranforderung erforderlich, bevor ein beobachteter Wert vorhanden ist. Turning browser Authorization off stops that captured value being supplied by the helper.

Wenn Sie im Browser „User-Agent“ oder „Accept-Language“ auswählen, werden nur diese HTTP-Felder geändert. Es führt kein Ziel-JavaScript aus, aktualisiert kein Body-CSRF-Token, reproduziert kein Browser-TLS und garantiert keine WAF-Akzeptanz. IP-/gerätegebundene Authentifizierung und OAuth-Aktualisierung benötigen weiterhin ihren Anwendungsworkflow.

VHOST / Host-Verwaltung

Der native Helfer ersetzt keinen internen Bridge-Alias im Host-Feld des Tools. Lassen Sie das Tool den Host-Wert senden, der für den autorisierten virtuellen Host-Test benötigt wird. Bei HTTPS bleibt das CONNECT-Ziel das autorisierte Ziel, während der Host-Header des Tools beibehalten werden kann.

Durch das Ändern eines Host-Headers wird kein Zugriff auf ein anderes Netzwerkziel gewährt. Ein Reverse-Proxy kann es an eine andere Anwendung weiterleiten; Beziehen Sie dieses Verhalten des virtuellen Hosts in die Autorisierung der Bewertung ein. Genaue fehlerhafte Header-Bytes und widersprüchliche Framings liegen außerhalb dieses analysierten Proxys.

Audit and privacy

Nativer Verkehr Zeigt Anforderungsmetadaten und geänderte/geschützte Feldnamen an. Bei der Prüfung werden geheime Cookie-/Header-Werte, Abfragewerte und Textkörper weggelassen. Dies bedeutet nicht, dass der Proxy niemals Geheimnisse verarbeitet: Er muss sie verarbeiten, um authentifizierten Datenverkehr zu senden. Externe Tools verwalten ihre eigenen Historien/Ergebnisse, die diese Werte enthalten können.

Halten Sie private Konfigurationstoken, CA-Schlüssel und Datenverzeichnisse von Berichten/Quellarchiven fern. Durch das Herunterladen der Konfiguration mit benutzerdefinierten Autorisierungswerten kann eine Datei erstellt werden, die diese Werte enthält.

    ProxyHandler({"http": proxy, "https": proxy}),
    ProxyBasicAuthHandler(credentials),
)

Pause und Fehler

Pausieren Sie native Anfragen blockiert neuen nativen Egress. Auch Authentifizierungsstatus 401/419/440, HTTP 429, Tab-Schließung/Off-Origin-Änderungen oder Budgetlimits können die Arbeit unterbrechen. Fahren Sie fort, nachdem Sie die Registerkarte überprüft haben wird erst wieder aufgenommen, nachdem der Kopplungsstatus überprüft wurde.

Anhalten und trennen beendet die Browser-Kopplung; Der separat gestartete Node-Prozess wird dadurch nicht beendet. Verwenden Sie Strg+C im Terminal, um diesen Vorgang zu stoppen.

Anfragen während des Flugs können beendet werden. Proxy-Clients erhalten Fehlermeldungen für blockierte Arbeit; Der Adapter unterbricht keine beliebigen Tool-Prozesse und spielt deren Anforderungen nicht ab. Überprüfen Sie, welche Anfragen erfolgreich waren, und verwenden Sie die eigenen Wiederholungs-/Fortsetzungssteuerungen des Tools. Durch einen Neustart/eine erneute Kopplung wird das Token geändert und eine Aktualisierung der Tool-Authentifizierung erforderlich.

401/419/440 kann bei absichtlich negativen Authentifizierungstests erwartet werden. Bei Bedarf anpassen session.pauseStatuses für diesen überprüften Lauf und Neustart; Der Adapter leitet nicht ab, ob es sich bei jedem Authentifizierungsfehler um eine beabsichtigte Prüfung handelt.

Tor- und Zwiebelrouting

Browserbasierte Longshot-Anfragen folgen dem Netzwerk des ausgewählten Browsers. Der native Adapter ist ein anderer Prozess und erbt nicht die Proxy-Einstellungen des Firefox/Tor-Browsers.

SOCKS/Tor ist standardmäßig deaktiviert in der nativen Konfiguration. Verwenden Sie für eine autorisierte Onion-Bewertung einen explizit konfigurierten vorhandenen SOCKS-Dienst mit Remote-Hostnamenauflösung, zum Beispiel diese Überschreibung, wenn das wirklich Ihr lokaler Tor-Listener ist:

{
  "routing": {
    "socks5": "socks5h://127.0.0.1:9050"
  }
}

In diesem Beispiel wird Tor nicht gestartet und es wird nicht festgestellt, dass Port 9050 existiert. Wählen Sie den tatsächlich konfigurierten Dienst aus; Eine Tor-Browser-Instanz verwendet möglicherweise einen anderen Listener. Starten Sie den Adapter neu und koppeln Sie ihn erneut. Ein HTTP(S) upstream.url und routing.socks5 schließen sich gegenseitig aus.

Der native Shim löst Hostnamen über SOCKS auf und verfügt über keinen stillen direkten Fallback. Ohne eine explizit konfigurierte Upstream-/SOCKS-Route werden direkte Onion-Ziele vor dem Ziel-DNS abgelehnt. Eine SOCKS-URL kann sich auch auf einen autorisierten SSH-Tunnel oder einen anderen SOCKS5-Dienst beziehen; es ist nicht unbedingt ein Beweis für das Tor-Routing.

Durch die Cookie-Freigabe wird die Exit-IP-Adresse oder der TLS-/Browser-Fingerabdruck der nativen Route nicht mit denen von Firefox identisch. Herausforderungen oder Sitzungsbindungen können dies ablehnen. Überprüfen Sie die Route und die erwartete Sitzung unabhängig voneinander.

Isolierte native Nuclei, die von der Agent-API gestartet werden, sind anders: Sein eingebautes Relay verfügt über keine Tor/SOCKS-Route und blockiert Onion-Ziele vor dem System-DNS. Verwenden Sie geeignete browserseitige Prüfungen im vorgesehenen Browser oder ein separat konfiguriertes externes Tool über den nativen Proxy. Gehen Sie nicht davon aus, dass das Kontrollkästchen Nuclei erbt routing.socks5 von Browser Bridge.

API-Explorer

Zuerst eine Verbindung herstellen und durchsuchen, dann auswählen Überprüfen Sie die aktuelle Seite. Importieren Sie eine vom Entwickler bereitgestellte Datei OpenAPI JSON Beschreibung, sofern verfügbar, bis zu 2 MB. Es liest lokales JSON, keine beliebige Remote-Seite oder YAML-Datei. Lokale Spezifikationsreferenzen und verfügbare Anfragebeispiele/Standards können konkrete unterstützte Eingaben liefern; Fehlende Werte/Körper und nicht unterstützte Konstrukte hinterlassen Lücken.

Ein Endpunkt ist eine Adresse; Eine Operation ist eine Adresse plus Methode. Abfrageeingaben werden danach angezeigt ?, Pfadeingaben im Adresspfad und Texteingaben im übermittelten Inhalt. Bei einem aufgeführten Vorgang handelt es sich um eine Bestandsaufnahme, nicht um einen Beweis dafür, dass das aktuelle Konto auf jedes Objekt, auf das es sich bezieht, zugreifen kann.

Benutzen Repeater neben einer unterstützten GET/HEAD-Operation, um eine Anfrage vorzubereiten, ohne sie noch zu senden. Überprüfen Sie URL/Methode/Eingaben und senden Sie sie dann gezielt. Bei reinen Inventarschreibvorgängen müssen Sie weiterhin die entsprechende Anfrage vorbereiten und eine Schreibgenehmigung einholen.

Repeater und Vergleich

Der Repeater stellt mithilfe der gebundenen Browsersitzung eine neue bereichsbezogene Anfrage. GET/HEAD/OPTIONS verwenden die normale Route. Schreibmethoden, Körperänderungen und Zerstörungs-/Upload-Funktionen unterliegen weiterhin den Richtlinien und der Genehmigung. Verwaltete Cookie-/Autorisierungs-/Hostwerte können nicht frei über den Header-Editor ersetzt werden. Verwenden Sie die native Route des externen Tools für explizit konfigurierte Header-/Cookie-Tests.

Folgen Sie Weiterleitungen gleichen Ursprungs steuert, ob Sie die Weiterleitung selbst oder die zulässige endgültige Antwort überprüfen. Weiterleitungen außerhalb des Gültigkeitsbereichs stellen keine pauschale Autorisierung dar. Behalten Sie die Antworttexte bei Bedarf zur Überprüfung bei und wählen Sie dann zwei gespeicherte Antworten aus Vergleichen. Compare sendet keine Anfragen; Dynamischer Inhalt, Anmeldestatus, Drosselung oder WAF-Seiten können einen Unterschied erklären.

WebSocket, SSE und Dienstprogramme

Wählen Sie einen entdeckten Kanal im Geltungsbereich aus oder geben Sie dessen genaue URL ein. Das Abhören und das Senden benutzerdefinierter Frames sind begrenzte, genehmigte Vorgänge und kein allgemeiner Protokollscanner. Der erfasste Fehlertext ist ein Hinweis; Es stellt keine Nachrichtenautorisierung oder einen Rassen-/Logikfehler dar.

Dienstprogramme kodieren/dekodieren Werte, berechnen SHA-256, formatieren JSON und prüfen JWT-Ansprüche lokal. Das Dekodieren eines JWT ist keine Signaturüberprüfung und stellt nicht sicher, dass der Server ein gefälschtes Token akzeptiert. Transformierte Eingaben werden nicht automatisch ausgeführt oder übermittelt.

Interpretieren der tatsächlichen Laufabdeckung

Die vollständige WSTG-Referenzkarte umfasst automatisierte Teilmengen, unterstützte Arbeit und manuelle Bewertung. In Tatsächliche Eingabeabdeckung:

  • Abgeschlossen bedeutet, dass die implementierte Regel für diese Eingabe abgeschlossen ist und nicht, dass die Eingabe sicher ist.
  • Teilweise bedeutet, dass einige Arbeiten ausgeführt wurden, aber ein Limit, eine Unterbrechung oder eine andere Bedingung den Abschluss verhinderte.
  • Übersprungen bedeutet, dass die Regel/Eingabe nicht ausgeführt wurde; Überprüfen Sie den Grund.

Eine WAF, eine fehlende Rolle, eine ungültige Sitzung, ein ausgeblendeter/nicht besuchter Workflow, ein nicht verfügbarer Anforderungstext, ein CSP oder ein erschöpftes Budget können dazu führen, dass eine anfällige Eingabe ungetestet bleibt. Durch die native Proxy-Kopplung werden diese Einschränkungen nicht vom integrierten Scanner entfernt. Eine beobachtete CVE-Version, ein fehlender Header oder eine andere Antwort ist nicht automatisch ein Exploit.

Version 2.18.1 hat 192 automatisierte Unit-/Regressionstests, acht echte Chrome-Prüfungen und acht echte Firefox-Prüfungen bestanden, einschließlich ZIP/YAML-CSP-Überprüfung und nativem ZAP-Verkehr gegen ein eigenes SQLite-Fixture. Seine offiziellen Browser-Bibliotheken werden Byte für Byte überprüft und ein sauberer Source-Rebuild reproduziert den Firefox XPI exakt. Diese Tests validieren das benannte Implementierungsverhalten; Sie zeigen nicht die Erkennung jeder Juice Shop-, WebGoat-, bWAPP- oder NodeGoat-Herausforderung an. Das externe ZAP SQLi-Ergebnis überprüft den Proxy-Pfad und nicht den Rückruf von Longshot über alle Schwachstellen hinweg.

Browserspeicher und optionale Sitzungsdateien

Der Browserspeicher bleibt unabhängig von einer der lokalen Bridges aktiv. Es speichert pro Profil den Verlauf, Ergebnisse, Bewertungen, Inventar und Optionen. Antworttexte können mit bestmöglicher Schwärzung beibehalten werden; Der vom Browser beobachtete Datenverkehr enthält häufig Metadaten ohne erfassten Text.

Für automatische Dateiprüfpunkte:

  1. Registrieren/verbinden Agent-API, nicht nur Browser Bridge.
  2. Offen Einstellungen → Beurteilungssitzungen → Anleitung.
  3. Geben Sie einen absoluten Wert ein Sitzungsordner auf dem Agent-API-Computer.
  4. Aktivieren Sitzungsdateien automatisch speichern und wählen Sitzungseinstellungen speichern.
  5. Benutzen Sitzung jetzt speichern für einen sofortigen Kontrollpunkt; Normale Änderungen lösen auch Speicherungen aus.
  6. Benutzen Aktuelle Sitzung exportieren / Sitzungsdatei importieren für manuelle Übertragung; Für den manuellen Import ist der native Host nicht erforderlich.

Dateien verwenden stabile Profil-IDs mit .longshot.json, was explizite Profile für einen Ursprung zulässt. Es handelt sich um lesbare, unverschlüsselte Bewertungsarchive, die Antragsdaten, verfasste Vorlagen und aufbewahrte Stellen enthalten können. Ausgenommen sind vom Browser verwaltete Cookies, Provider-Tokens und Ausführungszuschüsse.

Schreibvorgänge sind atomare Prüfpunkte für private Dateien. Bei einem abrupten Abbruch kann nur der zuletzt abgeschlossene Speicher wiederhergestellt werden. Wiederhergestellte laufende Scans werden unterbrochen. Wenn die Brücke getrennt wird, wird die Browserspeicherung fortgesetzt und die Dateispeicherung wartet; Nicht aufgelöste aktivierte Prüfpunkte erfordern möglicherweise eine erneute Verbindung oder die Deaktivierung der Dateispeicherung, bevor das Ziel gewechselt wird. Die maximale Größe der Sitzungsdatei beträgt 256 MB mit einem expliziten Fehler.

Der Export des Bewertungsarchivs unterscheidet sich von Konfiguration herunterladen in Browser Bridge. Ersteres speichert Bewertungsnachweise/-optionen; Letzteres speichert native Proxy-Einstellungen.
